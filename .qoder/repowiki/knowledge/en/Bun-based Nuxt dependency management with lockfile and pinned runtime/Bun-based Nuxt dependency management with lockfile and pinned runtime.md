This project manages JavaScript/TypeScript dependencies for a Nuxt 4 application shell using the Bun package manager. The approach is straightforward: a single root `package.json` declares all runtime and development dependencies, and a committed `bun.lock` file pins every transitive resolution to exact versions so installs are deterministic across machines.

**System used**
- Package manager: **Bun** (not npm/yarn/pnpm). Evidence is the presence of `bun.lock` at the repository root and the absence of any other lockfile or `.npmrc` / `yarn.lock` / `pnpm-lock.yaml`.
- Runtime framework: **Nuxt 4** (`nuxt` ^4.3.1), which drives the build pipeline via Vite and consumes the dependency tree declared in `package.json`.
- No vendoring strategy — all third-party packages are installed from the public registry into `node_modules` at install time.

**Key files**
- `package.json` — single source of truth for declared dependencies and devDependencies; scripts wire `nuxt build/dev/generate/preview` and `vitest`.
- `bun.lock` — full lockfile generated by Bun that records every resolved package, its integrity hash, and platform-specific binaries (e.g. `@esbuild/*`, `@mapbox/node-pre-gyp`).
- `nuxt.config.ts` — registers Nuxt modules (`@nuxt/ui`, `@pinia/nuxt`, `@pinia-plugin-persistedstate/nuxt`) and pre-bundles heavy deps like `xlsx` via Vite's `optimizeDeps.include`.
- `tsconfig.json` / `vitest.config.ts` — type and test tooling consumed as devDependencies.

**Architecture and conventions**
- Single-package monorepo: there are no workspaces or sub-packages; everything lives under one root `package.json`.
- Dependencies are split cleanly between `dependencies` (runtime: Nuxt, Vue, Pinia, TomTom Maps SDK, XLSX) and `devDependencies` (Vitest, Happy DOM, fast-check, @vue/test-utils).
- Version ranges use caret (`^`) semantics, but the lockfile freezes them to exact versions at install time, ensuring reproducible builds.
- A `postinstall` script runs `nuxt prepare`, so the Nuxt type layer is regenerated after every install.
- Heavy or ESM-only packages (`xlsx`) are explicitly listed in `vite.optimizeDeps.include` to avoid cold-start warnings.

**Rules developers should follow**
- Always run `bun install` (or `bun i`) rather than npm/yarn/pnpm so the correct lockfile format is produced.
- Commit `bun.lock` alongside `package.json`; never regenerate it without reviewing changes, since it pins exact transitive resolutions.
- Add new runtime libraries to `dependencies` and dev-only tooling to `devDependencies` in `package.json` — do not introduce separate lockfiles or workspaces.
- If a package ships native binaries (like `xlsx`'s underlying C++ libs), ensure the CI runner matches the host OS recorded in `bun.lock` or re-run `bun install` on the target platform to refresh the lockfile.
- Keep `nuxt.config.ts` in sync when registering new Nuxt modules so the same module list is available in both dev and production builds.
